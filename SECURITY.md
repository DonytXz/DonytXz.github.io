# Security and availability

## Hosting boundary

The portfolio is static HTML, CSS, and browser JavaScript on GitHub Pages at
`https://donatoalvarez.dev/`. Cloudflare is the authoritative DNS provider. The
chosen configuration is **DNS-only (gray cloud)**, with balanced access for
visitors, search engines, and link previews.

Cloudflare's HTTP DDoS mitigation, WAF, bot filtering, rate limiting, and CDN
caching do **not** apply to DNS-only website traffic. GitHub handles website
delivery and provider-level rate limiting. There is no application server or API
here on which to install an IP firewall or request limiter. DNSSEC, CSP, and
`robots.txt` do not prevent HTTP floods; crawler directives are voluntary.

GitHub Pages documents a **soft 100 GB/month bandwidth limit** and possible HTTP
429 responses. Neither this repository nor the hosting arrangement guarantees
uninterrupted availability. Keep the site lightweight and the report lazy-loaded.
Avoid adding auto-refresh loops, unnecessary remote scripts, or large downloads
to the initial page.

## Repository controls

- `astro.config.mjs` enables Astro's static, hash-based CSP. The portfolio allows
  same-origin resources and the data-URL favicon, blocks external network connections,
  inline event handlers, plugins, base-URL changes, and form submissions, and
  permits the same-origin report frame.
  Same-origin reads remain available to browser-based audit and crawler tools.
- `src/scripts/early-preferences.js` is trusted build input, emitted before paint.
  `BaseLayout.astro` hashes its exact normalized contents. Changes to that file
  automatically generate a new hash; a blanket `unsafe-inline` script allowance
  is unnecessary. Both generated HTML documents have an explicit referrer policy.
- `npm run build` runs `scripts/harden-html.mjs` after Astro. It moves Astro's
  generated policy before scripts and resource links, retaining charset first.
  This covers the pre-paint preference script as well as bundled scripts. The copied
  Lighthouse HTML needs its **own** policy: only its generated inline scripts are
  hashed and approved. The report needs inline styles for its renderer, but has
  no inline-script, remote-script, fetch, or child-frame allowance. The build
  fails if its expected script format changes. The original report in `public/`
  remains the measured artifact; hardening applies to the published `dist/` copy.
- GitHub Pages does not interpret `_headers`, `.htaccess`, or arbitrary Astro
  response headers as hosting configuration. HTML meta CSP cannot implement
  `frame-ancestors`, response-header-only protections, or report-only CSP.
- Direct workflow Action references use verified upstream commit SHAs, with
  version comments. Review the action code and its own dependencies when updating
  a pin; pinning a wrapper does not pin mutable references inside that wrapper.
- Dependabot proposes weekly npm and GitHub Actions updates. Review and test them
  before merging. The lockfile and `npm ci` keep dependency installation repeatable.
  CI also runs `npm audit --audit-level=high` across build and runtime dependencies.
  Review advisories rather than applying unreviewed force-upgrades to clear a gate.
- CI and availability checks have read-only repository permissions. Only the
  deployment job receives Pages-write and OIDC permissions. Publishing requires
  `main` and the original repository, including manual dispatch.

## Account setup checklist

These settings require the owner's authenticated dashboards; repository files do
not enable them. Record completion only after checking the live setting.

### 1. Verify GitHub Pages domain ownership

1. Open **GitHub personal Settings → Pages**, rather than repository Settings.
2. Add `donatoalvarez.dev` to verified domains, or check its existing status.
3. In Cloudflare DNS, add the TXT name and value generated by GitHub. For this
   account the expected name is
   `_github-pages-challenge-DonytXz.donatoalvarez.dev`. Use the real generated value;
   do not invent a verification token.
4. Confirm the record is visible, then select **Verify** in GitHub. Retain the TXT
   record to keep verification active.
5. Review DNS for dangling Pages records and wildcard records such as `*`. Remove
   an obsolete record only after checking what uses it. Keep the existing apex A
   and AAAA records and `www` CNAME serving the site.
6. Confirm repository **Settings → Pages** has the intended domain and **Enforce
   HTTPS** enabled. The public HTTPS redirect already works; a live redirect is
   not proof of the account's domain-verification status.

Initial public checks during this hardening review did not return the expected
ownership TXT record. Check the dashboard and DNS again before acting.

### 2. Enable and validate DNSSEC

1. Open **Cloudflare → domain → DNS → Settings → DNSSEC** and enable signing.
2. If Cloudflare is also the registrar, use its integrated DS registration flow.
   Otherwise, enter Cloudflare's exact DS values in the actual registrar's DNSSEC
   settings. A DS record belongs at the parent via the registrar, not as an
   ordinary record inside this zone.
3. Wait for the registrar/parent-zone update. Confirm the DS and DNSKEY records
   are published and validate the full chain with a DNSSEC validator such as
   [DNSViz](https://dnsviz.net/). Check resolution using multiple validating
   resolvers and confirm the website and email still work.

Initial checks returned neither a DS record nor DNSKEY records. DNSSEC protects
DNS authenticity, not request volume. Publishing DS values that do not match the
active signing keys can cause validating resolvers to return `SERVFAIL`.

PowerShell record checks (record presence alone is not full chain validation):

```powershell
Resolve-DnsName -Name _github-pages-challenge-DonytXz.donatoalvarez.dev -Type TXT
Resolve-DnsName -Name donatoalvarez.dev -Type DS -Server 1.1.1.1
Resolve-DnsName -Name donatoalvarez.dev -Type DNSKEY -Server 1.1.1.1
Resolve-DnsName -Name donatoalvarez.dev -Type A -Server 8.8.8.8
```

### 3. Protect accounts and publishing

- Enable passkeys/security-key-based two-factor authentication for GitHub,
  Cloudflare, the registrar if separate, and recovery email. Store recovery codes
  securely and review account sessions and API tokens. Use narrowly scoped tokens
  for any later automation, not an account-wide API key in this repository.
- Confirm domain auto-renewal, payment details, expiration reminders, transfer
  lock, and a working recovery contact independent of this domain.
- Add a `main` branch ruleset requiring pull requests and the existing **Portfolio
  checks** job to pass. Prevent force pushes and deletion. Keep any reviewer
  requirement practical for a single-maintainer repository.
- Restrict the `github-pages` environment to `main`. Retain both the deployment
  workflow's push-branch filter and job-level repository/ref guards.
- Enable Dependabot alerts/security updates and secret scanning/push protection
  where available. Verify Actions failure notifications reach the owner. Dashboard
  notifications, scanning, and branch rules are not configured by Dependabot YAML.

## Monitoring

Run the bounded, read-only production probe with Node 24:

```sh
npm run check:site
```

It makes one homepage GET and two redirect HEAD requests, with a 15-second timeout
per request. It verifies the expected content, canonical redirects, normal TLS
chain/hostname validation, and more than 14 days remaining on the HTTPS
certificates. Unexpected statuses (including 429/5xx), DNS/network errors, content
mismatches, or certificate problems produce a nonzero exit. This is not a load
test, traffic counter, DNSSEC validator, or attack detector.

`.github/workflows/monitor.yml` runs the probe twice an hour after reaching `main`
in the original repository, and supports manual dispatch there. It installs no
project dependencies and has no deployment permissions. Enable GitHub Actions
failure notifications and run it manually once after release to confirm delivery.
Schedules may be delayed, and GitHub can disable scheduled workflows in public
repositories after 60 days without repository activity. GitHub monitoring shares
a provider with the host and cannot independently detect every GitHub outage.

Also configure an **external uptime service** through its dashboard:

- Check `https://donatoalvarez.dev/` every 1–5 minutes for HTTP 200 and expected
  portfolio text, with confirmation from a second location before alerting.
- Enable DNS/network failure and certificate-expiry alerts; monitor `www` TLS too.
- Deliver alerts to an independently reachable email address. Test a notification.
- Set a separate domain-expiration reminder and review it with registrar renewal.

That external service is an owner setup step; this repository does not provision
it. With DNS-only, Cloudflare HTTP security events and traffic analytics are not
available for these requests. Client-side analytics would also miss many bots.

## Verification and release

```sh
npm run format:check
npm run check
npm run build
npm run test:e2e
```

The browser suite uses production preview, where CSP is enforced. Security tests
attempt unauthorized inline scripts, event handlers, external fetches, and base changes
against both HTML documents. They also check that normal controls and the report
work without CSP violations. The existing suite covers themes, languages,
accessibility, no-JavaScript usage, storage failures, and print behavior.

After meaningful page changes, refresh the production-preview audit with
`npm run preview`, `npm run audit`, and `npm run build`. Review measured metadata
and rerun affected browser checks. Rebuilding reapplies report CSP to the fresh
artifact. The report describes the production preview, not the live domain.

Deliver through a reviewed feature-branch PR. After an authorized merge/release,
run `npm run check:site` and check the live homepage and report in a browser,
including the actual emitted meta CSP and console. Apply dashboard changes one at
a time, validating resolution and HTTPS after each.

## Incident response and rollback

1. Confirm the failure from another network or monitoring region. Record the
   time, affected URL, status code, and request ID if present. Check
   [GitHub Status](https://www.githubstatus.com/) and
   [Cloudflare Status](https://www.cloudflarestatus.com/).
2. Separate DNS failures, certificate errors, HTTP 429/5xx, and bad content. Review
   the last deployment and recent DNS/account changes. Repeatedly deploying a
   working static page does not resolve a provider outage or request flood.
3. For a bad release, revert the offending change through a PR and redeploy the
   last known-good content via the main-only workflow. For CSP regressions, inspect
   the violation and correct the allowed resource/hash rather than granting
   blanket script execution. A reviewed revert of the CSP change is the fallback.
4. For sustained provider rate limiting or suspected abuse, retain the evidence
   and contact GitHub Support. No local JavaScript change can reject requests
   before they reach GitHub Pages in this DNS-only configuration.
5. For DNSSEC rollback, remove the parent DS record via the registrar (or use
   Cloudflare Registrar's documented disable flow). Keep signing active until the
   parent DS TTL has expired before disabling it. Follow the current provider
   procedure; disabling signing while a DS is still cached can prolong downtime.
6. For suspected account compromise, secure the account, revoke affected tokens,
   inspect DNS and deployment history, and restore the verified configuration.

Report suspected vulnerabilities privately to `me@donatoalvarez.dev`; avoid
publishing credentials or sensitive details in public issues.
